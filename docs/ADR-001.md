# ADR 001 — monorepositorio TypeScript con arquitectura por capas

Estado: decisión inicial para el desarrollo incremental.

## Contexto y decisión

El proyecto debe servir a un piloto de la Red Pasco y permitir expansión por redes asistenciales. Se elige Next.js + NestJS + Prisma para compartir el lenguaje entre cliente y servidor, con PostgreSQL como fuente de verdad y Redis para tareas efímeras. Go queda fuera de la implementación inicial para mantener un solo backend.

Se reservan cuatro capas en `apps/api/src`. El dominio contiene entidades, invariantes y puertos sin imports de NestJS, Prisma ni HTTP. Aplicación coordina casos de uso sobre esos puertos. Infraestructura implementa persistencia e integraciones. Presentación adapta HTTP y eventos a los casos de uso. El módulo de composición de NestJS conectará las implementaciones en 1.4.

## Requisitos que condicionan las próximas subetapas

- En 1.2, `red_asistencial_id` identifica el tenant; centros y áreas deben conservar pertenencia mediante claves compuestas y restricciones. El alcance se obtiene de identidad autenticada, no de un tenant elegido libremente en una cabecera. Habrá roles de base separados y defensa en profundidad con PostgreSQL RLS; deben probarse lecturas y escrituras cruzadas entre tenants.
- En 1.3, cada mutación y su auditoría se guardarán en la misma transacción. Se restringirán UPDATE, DELETE y TRUNCATE para el rol de aplicación sobre audit logs. Se documentará el límite: un superusuario de PostgreSQL puede alterar controles; una garantía contra administradores exige almacenamiento externo con retención protegida. No se prometerá inmutabilidad absoluta con una tabla ordinaria.
- La API funcional se implementa después de esos controles. En 3.1 se añade JWT y RBAC; antes de habilitarlo, los endpoints de negocio no deben quedar expuestos a acceso público sin autenticación.
- En 2.3, las suscripciones en tiempo real deben autorizar tenant y alcance; Redis no será la fuente persistente de tickets ni auditoría.
- En 3.4, el modo offline requiere cola idempotente, resolución de conflictos y limpieza de datos al cerrar sesión. Un service worker por sí solo no cubre estos requisitos.
- Node-RED se integra desde 4.2 mediante interfaces autenticadas de aplicación; no escribirá tickets directamente en PostgreSQL.

## Consecuencias

El monorepositorio facilita revisar cambios de contrato. Los contratos compartidos no exponen entidades ORM ni credenciales. Multi-tenancy nacional es un objetivo de diseño que debe demostrarse con pruebas; la estructura vacía de esta entrega no lo implementa todavía. El catálogo de centros de la Red Pasco se validará con una fuente institucional en 3.2 antes de tratarlo como dato real.
